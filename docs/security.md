# PocketClaw Security & Threat Model

PocketClaw lets a phone approve actions of an autonomous coding agent on your Mac.
That is a serious capability, so the security posture is documented explicitly here.

## Design stance

**Transport-private, single-user.** PocketClaw is designed to run entirely inside a
[Tailscale](https://tailscale.com) tailnet (or, at minimum, a trusted LAN). There is
no third-party relay, no cloud account, and no public endpoint. The threat model
assumes **one user who owns both devices and the tailnet**.

## Trust boundaries

```
[ iPhone app + widget ]  ──tailnet──▶  [ host daemon ]  ──local──▶  [ Claude Code sessions ]
        trusted                            trusted                  semi-trusted (the agent
                                                                    is the thing we gate)
```

The entity being constrained is **the agent**, not the network peer: risk tiers and
the permission flow exist so that a Claude session cannot take destructive actions
without explicit, informed human consent.

## Controls

### 1. Tailnet assumption

The host binds `0.0.0.0:8787` but is expected to be reachable only over the tailnet.
Tailscale provides device identity, WireGuard encryption, and ACLs. **Do not port-forward
8787 to the public internet.** If you must run outside a tailnet, put the daemon behind
a reverse proxy with TLS — token auth alone is not designed for hostile networks.

### 2. Token handling

- A single random bearer token is generated by `pocketclaw init` (cryptographically
  random, stored in `~/.pocketclaw/config.json` with user-only file permissions).
- Required on every WS connect (`?token=`) and every REST call (`Authorization: Bearer`).
- The host compares tokens with a **constant-time comparison**
  (`crypto.timingSafeEqual` over equal-length digests) to prevent timing side channels.
- The token transits as a query parameter on WS connect; this is acceptable inside a
  WireGuard-encrypted tailnet but is one reason the public-internet deployment is
  unsupported.
- Rotate by re-running `pocketclaw init` and re-pairing the app (scan the new QR).

### 3. Default-deny timeout

Every permission request has a deadline. If no decision arrives in time, the host
resolves it as **deny** and broadcasts `permission_resolved` with `behavior: "deny"`.
A dead phone, a dropped connection, or simple inattention can never silently grant
the agent anything.

### 4. Risk tiers and the Live Activity rule

Tiers are computed **host-side** (`packages/shared/src/risk.ts`) — the client merely
displays them and can never upgrade its own privileges:

- `low` (Read, Grep, Glob, WebSearch, TodoWrite, Task, NotebookRead): auto-allowed,
  still written to the audit log.
- `medium` (Edit, Write, non-dangerous Bash, WebFetch, `mcp__*`): requires a decision;
  may be approved from the Live Activity / Dynamic Island.
- `high` (Bash matching `rm -rf`, `sudo`, `--force`, `git push --force`, `mkfs`,
  `shutdown`, `reboot`, `deploy`, `publish`, redirects into `/dev`; any tool name
  matching `delete`/`remove`): requires a decision, and the Live Activity offers
  **only "Open app"**.

**Why high-risk is excluded from Live Activity actions.** Lock-screen buttons are
optimized for speed: a glance and a tap, often without unlocking. That is exactly
the wrong affordance for destructive operations — the truncated `inputPreview` on a
Live Activity cannot convey the full command, and muscle-memory taps are a real
failure mode. Forcing "unlock → open app → read the full input → decide" adds the
friction that destructive actions deserve. This is enforced in **both** layers: the
widget never renders an Approve button for `high`, and the host independently
validates the tier on `POST /api/decision`, so a forged or buggy client cannot
bypass it.

### 5. Audit log

Every permission event is appended to `~/.pocketclaw/audit.jsonl` — one JSON object
per line: request id, session, tool, full input (not just the preview), computed
tier, the decision (`allow` / `deny`), how it was decided (client decision,
auto-allow, or timeout), an optional note, and timestamps. Append-only by
convention; review it with `jq` or ship it to your log pipeline.

## Known gaps (honest list)

- **No end-to-end encryption yet.** Confidentiality currently rests entirely on the
  tailnet (WireGuard). Anyone with a device on your tailnet and the bearer token has
  full control. This matches the single-user-tailnet threat model, but E2EE (so the
  host relay could be untrusted) is on the roadmap.
- **Single token, full privileges.** No per-client scoping, no read-only tokens.
- **Token at rest on iOS.** The app stores the bearer token in AsyncStorage and
  mirrors it into the App Group `UserDefaults` so the Live Activity intent can
  reach the host. Both are sandboxed but unencrypted; moving to Keychain items
  (`kSecAttrAccessibleWhenUnlockedThisDeviceOnly`, shared access group) is on the
  roadmap.
- **Regex-based high-risk detection** can be evaded by obfuscated shell (e.g.
  `r''m -rf`, base64-piped commands). Tiers are a usability layer on top of the
  default-deny flow, not a sandbox. Defense in depth: run the host as a
  non-privileged user and rely on Claude Code's own workspace boundaries.
- **No rate limiting** on the REST endpoints (tailnet assumption again).
- **QR pairing payload contains the token** — anyone who photographs your terminal
  during `pocketclaw serve` can pair. Re-run `pocketclaw init` if that happens.
